# Macgly — Full Technical, Commercial & Compliance Audit

**Date:** 30 July 2026
**Scope:** https://www.macgly.com + full source (`apps/api`, `apps/web`), commit `8c092ae`
**Method:** Source-code review of every controller, model, route, service and page; live HTML/robots.txt fetch; production build artefact analysis. No runtime DB access, no Lighthouse run (see *Verification Gaps* at the end).
**Positioning claim under test:** "India's best industrial B2B marketplace, competing with Moglix / IndustryBuying / IndiaMART / Amazon Business / Zoro / Grainger."

---

## 1. Executive Summary

Macgly is a **broad but shallow B2C storefront wearing B2B language**. The team has shipped an impressive amount of surface area — vendors, affiliates, KYC wizards, ad campaigns, warranties, returns, CRM, coupons, commissions, manual orders. That breadth is real and it is not nothing.

But almost none of it is *correct*, *secure*, or *B2B*.

Three findings alone would stop a funding due-diligence:

1. **Every anonymous visitor on the site shares one single cart document.** `cartController.js` falls back to `sessionId: 'anon'` and no code anywhere ever sets a `sessionId` cookie. `Cart.sessionId` is `unique: true`. There is therefore exactly **one** guest cart in the database, globally. Guest A adds a drill; Guest B in another city sees it. Worse: the first logged-in user without a cart *silently takes ownership of it*.
2. **A vendor can credit themselves unlimited money.** `POST /vendors/ads/wallet/recharge/verify` takes the credit `amount` **from the request body** and verifies a Razorpay signature that does not cover the amount. Pay ₹100, send `amount: 1000000`, get ₹10 lakh of ad credit. Replayable indefinitely with the same payment ID.
3. **Every "TAX INVOICE" issued is legally invalid.** No supplier GSTIN, no buyer GSTIN, no HSN per line, no CGST/SGST/IGST split, no place of supply, no invoice serial series, no TCS u/s 52. Rule 46 CGST is not met on any field that matters. On a marketplace the *vendor* must issue the invoice, not Macgly — that model does not exist in the code.

On top of that, the B2B thesis is not implemented at all. There is **no GSTIN field in checkout**, no company/billing entity, no RFQ or bulk-quote flow, no tiered/slab pricing, no MOQ, no credit terms, no NEFT/RTGS, no purchase-order number, no datasheet/manual downloads, no OEM part-number cross-reference, no compatibility matrix. Every one of those is table stakes at Moglix and Grainger. Macgly today is a small Tamil-Nadu-flavoured B2C tool shop with a vendor console bolted on.

The homepage — the single most valuable pixel real-estate you own — **displays zero products**. Hero, ten category tiles, one "Contact Us" CTA. The `/api/catalog/featured` endpoint exists and is never called.

And the entire site is invisible to non-Google crawlers: it is a client-rendered Vite SPA with **no SSR and no prerender**. WhatsApp, LinkedIn, Facebook and Twitter previews of any product link will show the generic homepage card forever. In an Indian B2B market where WhatsApp *is* the sales channel, this is a strategic wound, not a technical nit.

**Verdict: not production-grade. Do not scale marketing spend against this until P0s are closed.** The good news: the architecture is conventional (Express + Mongoose + React), the code is readable, and most P0s are 1–20 line fixes. This is recoverable in weeks, not quarters.

#### SEC-01 · P0 · Ad-wallet top-up amount is client-controlled and replayable
> **STATUS: RESOLVED — 31 Jul 2026 (P0-02).** The credited amount now comes from
> `rz.orders.fetch(...).amount_paid`; `req.body.amount` is ignored for crediting and only
> logged when it disagrees. Ownership and the expected amount are carried in server-set
> Razorpay `notes`. Replay is blocked by an atomic `'transactions.paymentId': { $ne: id }`
> guard on a single-document update. Signature comparison is now constant-time
> (`utils/razorpaySignature.js`).
>
> **Additional defect found while fixing:** the old `receipt` string
> (`adwallet_<24-char ObjectId>_<13-digit ms>`) was **47 characters** against Razorpay's
> documented 40-character limit. Shortened to 36. Ownership no longer depends on the
> receipt, so the limit can't silently break verification again.

**File:** [vendors.js:1045-1068](apps/api/src/routes/vendors.js#L1045-L1068)

```js
const { razorpayOrderId, razorpayPaymentId, razorpaySignature, amount } = req.body;
const expected = crypto.createHmac('sha256', RAZORPAY_KEY_SECRET)
  .update(`${razorpayOrderId}|${razorpayPaymentId}`).digest('hex');
if (expected !== razorpaySignature) throw new AppError(...);
const credit = Math.round(parseFloat(amount || 0) * 100) / 100;   // ← attacker-supplied
await AdWallet.findOneAndUpdate({ vendorId: req.user._id }, { $inc: { balance: credit, ... } }, { upsert: true });
```

**Why it matters.** The HMAC covers only `order_id|payment_id`. It says nothing about the amount. Any approved vendor can recharge ₹100, then POST the *same valid* triple with `amount: 10000000`, and repeat it in a loop. Direct, unbounded theft of ad inventory. There is also no check that `razorpayOrderId` was created by this vendor or for this purpose, and no idempotency — one legitimate payment can be redeemed a thousand times.

**Fix.** Fetch the real amount from Razorpay and enforce single-use:

```js
const rz = new Razorpay({ key_id: RAZORPAY_KEY_ID, key_secret: RAZORPAY_KEY_SECRET });
const rzOrder = await rz.orders.fetch(razorpayOrderId);

// 1. Must be a wallet order belonging to THIS vendor
if (!rzOrder.receipt?.startsWith(`adwallet_${req.user._id}_`)) {
  throw new AppError('Order mismatch', 400, 'INVALID_ORDER');
}
// 2. Must actually be paid
if (rzOrder.status !== 'paid') throw new AppError('Payment not captured', 400, 'NOT_PAID');
// 3. Amount comes from Razorpay, never the client
const credit = rzOrder.amount_paid / 100;
// 4. Single-use: unique index on transactions.paymentId
const wallet = await AdWallet.findOneAndUpdate(
  { vendorId: req.user._id, 'transactions.paymentId': { $ne: razorpayPaymentId } },
  { $inc: { balance: credit, totalRecharged: credit },
    $push: { transactions: { amount: credit, type: 'recharge', paymentId: razorpayPaymentId } } },
  { upsert: true, new: true }
);
if (!wallet) throw new AppError('Payment already redeemed', 409, 'DUPLICATE');
```

Also use `crypto.timingSafeEqual` for the signature comparison.

#### SEC-02 · P0 · One global shared cart for every anonymous visitor
> **STATUS: RESOLVED — 31 Jul 2026 (P0-01).** Per-browser session cookies are now issued by
> `apps/api/src/middleware/session.js`; cart ownership is centralised in
> `apps/api/src/services/cartService.js`. The `'anon'` fallback is gone and that literal is
> permanently rejected by session-id format validation. Guest→user migration merges atomically.
> Run `node apps/api/src/scripts/fixSharedGuestCart.js` once to purge the legacy shared cart.

**Files:** [cartController.js:6-25](apps/api/src/controllers/cartController.js#L6-L25), [orderController.js:38](apps/api/src/controllers/orderController.js#L38), [Cart.js:15](apps/api/src/models/Cart.js#L15)

```js
function cartFilter(req) {
  return req.user ? { user: req.user._id } : { sessionId: req.cookies.sessionId || 'anon' };
}
```

`grep -rn sessionId apps/api` returns **seven** hits — all *readers*. Nothing ever sets a `sessionId` cookie. Combined with `sessionId: { type: String, unique: true, sparse: true }`, the database contains exactly one guest cart, keyed `'anon'`, shared by the entire internet.

**Consequences:**
- Guest A's items appear in Guest B's cart (privacy + trust disaster).
- `resolveCart()` migrates the `'anon'` cart to the first logged-in user who lacks one — **cart theft**.
- Race conditions on `cart.save()` between concurrent guests silently drop items.

**Fix.** Issue a signed session cookie in a middleware ahead of the cart routes:

```js
// apps/api/src/middleware/session.js
const { randomUUID } = require('crypto');
module.exports = function ensureSession(req, res, next) {
  if (!req.cookies.sessionId) {
    const sid = randomUUID();
    res.cookie('sessionId', sid, {
      httpOnly: true, sameSite: 'lax', secure: isProd(),
      maxAge: 30 * 24 * 60 * 60 * 1000,
    });
    req.cookies.sessionId = sid;
  }
  next();
};
```

Then **never** fall back to `'anon'` — if there is no `sessionId`, return an empty cart. Add a one-off migration to delete the existing `{sessionId:'anon'}` document, and a TTL index (`updatedAt`, 30 days) on guest carts.

#### SEC-03 · P0 · Coupon discount survives cart mutation → free orders
> **RESOLVED — 31 Jul 2026 (RC-02).** `createOrder` recomputes the discount against its own
> subtotal via `utils/coupon.js`, revalidating expiry, usage limit and minimum order. The value
> on the cart is now a display convenience only. `computeCouponDiscount` clamps to
> `[0, subtotal]`, so the ₹0-order path is closed. The apply route uses the same helper.
**Files:** [cart.js:42-52](apps/api/src/routes/cart.js#L42-L52), [orderController.js:83,94](apps/api/src/controllers/orderController.js#L83-L94)

The discount is computed once at apply-time against the then-current subtotal and **persisted on the cart**. `createOrder` then blindly reads `cart.coupon.discount` and does `Math.max(0, subtotal - discount + shipping)`.

**Exploit:** cart worth ₹50,000 → apply a ₹5,000 flat coupon → remove items until subtotal is ₹4,900 → order total = `max(0, 4900 - 5000 + 0)` = **₹0**. Razorpay order of amount 0. Free goods, shipped.

**Fix.** Store only the coupon *code* on the cart. Recompute the discount server-side inside `createOrder` against the freshly-computed subtotal, and clamp it:

```js
let discount = 0;
if (cart.coupon?.code) {
  const c = await Coupon.findOne({ code: cart.coupon.code, active: true });
  if (c && (!c.expiry || c.expiry > new Date()) && subtotal >= (c.minOrderAmount || 0)) {
    discount = c.type === 'flat'
      ? Math.min(c.value, subtotal)
      : Math.min(subtotal * c.value / 100, c.maxDiscount > 0 ? c.maxDiscount : Infinity);
    discount = Math.min(parseFloat(discount.toFixed(2)), subtotal);   // never exceed subtotal
  }
}
```
Also add the per-user limit re-check here (currently only enforced at apply-time, so a user can apply → order → apply again in a race).

#### SEC-04 · P0 · Shipping charge is taken from the request body
> **RESOLVED — 31 Jul 2026 (RC-02).** `GET /catalog/shipping-rates` now records what it quoted
> per pincode (`utils/shippingQuote.js`, one-hour TTL on the existing cache), and `createOrder`
> bills the client's figure only when it matches a quoted rate for that pincode. Anything else
> — `0`, a negative, a rate quoted for a different pincode — falls back to the configured
> default. No carrier call was added to the checkout path and the frontend is unchanged.
**File:** [orderController.js:90-93](apps/api/src/controllers/orderController.js#L90-L93)

```js
const clientShipping = parseFloat(req.body.shippingCharge);
const shippingCharge = subtotal >= freeThreshold ? 0
  : (Number.isFinite(clientShipping) && clientShipping >= 0 ? clientShipping : serverShipping);
```

`POST /api/orders {"shippingCharge": 0}` → free express shipping on every order, forever. There is a genuine reason this exists (live Delhivery rates are fetched client-side), but the fix is to re-fetch or cache the quote server-side, never to trust the number.

**Fix.** Cache the quote against a server-issued token:

```js
// on GET /catalog/shipping-rates — cache the quote
const quoteId = randomUUID();
await setCache(`quote:${quoteId}`, { pincode, weight, options }, 900);
res.json({ quoteId, options });

// in createOrder — resolve, never trust
const quote = await getCache(`quote:${req.body.quoteId}`);
const chosen = quote?.options.find(o => o.id === req.body.shippingOptionId);
const shippingCharge = subtotal >= freeThreshold ? 0 : (chosen?.charge ?? serverShipping);
```

#### SEC-05 · P0 · Razorpay webhook uses the wrong secret and never fires
> **RESOLVED — 31 Jul 2026 (RC-02).** The `|| RAZORPAY_KEY_SECRET` fallback is gone,
> `isValidWebhookSignature()` compares with `crypto.timingSafeEqual` over the raw buffer, a
> missing raw body is rejected rather than silently re-serialised, and
> `RAZORPAY_WEBHOOK_SECRET` is now required at boot in production (verified: the process exits
> with `FATAL: Missing required environment variables: RAZORPAY_WEBHOOK_SECRET`). Declared in
> `render.yaml` alongside `RESEND_API_KEY`, `FRONTEND_URL`, `CSRF_SECRET` and `PLATFORM_GSTIN`.
**File:** [payments.js:20](apps/api/src/routes/payments.js#L20)

```js
const secret = RAZORPAY_WEBHOOK_SECRET || RAZORPAY_KEY_SECRET;
```

`render.yaml` does not declare `RAZORPAY_WEBHOOK_SECRET`. Razorpay signs webhooks with the *webhook* secret, so every real webhook fails signature verification and returns 400. **The entire webhook path is dead in production.** That means: if a customer pays and closes the tab before `/payments/verify` runs, the order stays `pending` forever, stock stays decremented, no confirmation email, no vendor notification, no commission record. `cleanupStaleOrders` will eventually cancel a *paid* order.

**Fix.** Set `RAZORPAY_WEBHOOK_SECRET` in Render, remove the fallback (fail loudly instead), and use a timing-safe compare:

```js
if (!RAZORPAY_WEBHOOK_SECRET) { console.error('WEBHOOK SECRET MISSING'); return res.status(500).end(); }
const expected = crypto.createHmac('sha256', RAZORPAY_WEBHOOK_SECRET).update(req.rawBody).digest('hex');
const ok = signature.length === expected.length &&
  crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected));
if (!ok) return res.status(400).json({ error: 'Invalid signature' });
```
Also exclude `/api/payments/webhook` from `apiLimiter` — Razorpay retries can be throttled by the 500-req/15-min global limit.

#### SEC-06 · P0 · No Content-Security-Policy on the actual website
**File:** [app.js:23-49](apps/api/src/app.js#L23-L49)

Helmet's CSP is configured carefully — and then applied to `macgly.onrender.com`, which serves only JSON. The pages users load come from **Vercel**, which sends no CSP, no `X-Frame-Options`, no `Referrer-Policy`, no `Permissions-Policy` at all. The CSP as written is also broken for its stated purpose: `scriptSrc` omits `https://checkout.razorpay.com`, which `Checkout.jsx` injects at runtime.

**Fix.** Move headers to `apps/web/vercel.json`:

```json
{
  "headers": [{
    "source": "/(.*)",
    "headers": [
      { "key": "Content-Security-Policy", "value": "default-src 'self'; script-src 'self' 'unsafe-inline' https://checkout.razorpay.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: blob: https://res.cloudinary.com; connect-src 'self' https://api.razorpay.com https://lumberjack.razorpay.com https://api.postalpincode.in https://nominatim.openstreetmap.org; frame-src https://api.razorpay.com https://checkout.razorpay.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'" },
      { "key": "X-Content-Type-Options", "value": "nosniff" },
      { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
      { "key": "Permissions-Policy", "value": "camera=(), microphone=(), payment=(self \"https://checkout.razorpay.com\")" },
      { "key": "Strict-Transport-Security", "value": "max-age=63072000; includeSubDomains; preload" }
    ]
  }]
}
```
Work toward removing `'unsafe-inline'` from `script-src` (nonce the inline loader) — right now it neuters most of the XSS protection CSP exists to give.

#### SEC-07 · P1 · Password policy is effectively absent
**Files:** [authController.js:31-67](apps/api/src/controllers/authController.js#L31-L67), [users.js:76](apps/api/src/routes/users.js#L76)

`register()` performs **no length or complexity check whatsoever** — `"a"` is a valid password. Reset and change require 6 characters. No breach-list check, no zxcvbn, no maximum length guard (bcrypt silently truncates at 72 bytes). `emailVerified` exists on the model and is never set or enforced anywhere — anyone can register with `ceo@tata.com`.

**Fix.** One shared validator, applied at all three entry points:

```js
// utils/password.js
const COMMON = new Set(['password','12345678','qwerty123','admin@123','india@123']);
function assertStrongPassword(pw) {
  if (typeof pw !== 'string' || pw.length < 10 || pw.length > 72)
    throw new AppError('Password must be 10–72 characters', 400, 'WEAK_PASSWORD');
  if (!/[a-z]/.test(pw) || !/[A-Z]/.test(pw) || !/\d/.test(pw))
    throw new AppError('Password needs upper case, lower case and a number', 400, 'WEAK_PASSWORD');
  if (COMMON.has(pw.toLowerCase())) throw new AppError('Password is too common', 400, 'WEAK_PASSWORD');
}
```
Then gate vendor/affiliate payouts on `emailVerified === true`.

#### SEC-08 · P1 · Login reveals which emails are registered
**File:** [authController.js:80-109](apps/api/src/controllers/authController.js#L80-L109)

Three separate oracles:
- `if (!user.isActive) throw 'Account is deactivated'` — thrown *before* the password check.
- `"Invalid credentials. 3 attempts remaining before lockout."` — an unregistered email never produces this message.
- No dummy bcrypt for unknown users → a measurable ~100 ms timing difference.

At 20 auth attempts / 15 min / IP this is slow, but a distributed scrape of your buyer list is entirely feasible and is exactly what a competitor would do.

**Fix.** Uniform message, uniform timing:

```js
const DUMMY_HASH = '$2a$12$abcdefghijklmnopqrstuv...'; // bcrypt of a random constant
const user = await User.findOne({ email }).select('+password +loginAttempts +lockUntil');
const isMatch = await bcrypt.compare(password, user?.password || DUMMY_HASH);
if (!user || !isMatch || !user.isActive) {
  // increment counters when user exists, but always return the same body
  throw new AppError('Invalid email or password', 401, 'INVALID_CREDENTIALS');
}
```
Lock on `email + IP` in Redis rather than only on the user document, so the lockout cannot be used to deny service to a known competitor's account.

#### SEC-09 · P1 · Authenticated file upload is an open bucket
**File:** [upload.js:7-37](apps/api/src/routes/upload.js#L7-L37)

Any authenticated **customer** can upload up to 10 files × 5 MB per request to `POST /api/upload/multiple`, into an **arbitrary, unvalidated `folder`** taken from the body. `fileFilter` trusts the client-declared `mimetype`, so a `.svg` (active content) or a polyglot payload declared as `image/png` passes. No magic-byte sniffing, no per-user quota, no dedicated rate limit.

**Fix.** Restrict to roles that need it, allowlist the folder, and verify content:

```js
const ALLOWED_FOLDERS = new Set(['products','kyc-documents','avatars','banners','carousel']);
const uploadLimiter = rateLimit({ windowMs: 60_000, max: 20 });

router.post('/multiple', authenticate, authorize(['vendor','admin']), uploadLimiter,
  upload.array('files', 10), async (req, res, next) => {
    const folder = ALLOWED_FOLDERS.has(req.body.folder) ? req.body.folder : 'uploads';
    for (const f of req.files) {
      const { fileTypeFromBuffer } = await import('file-type');
      const t = await fileTypeFromBuffer(f.buffer);
      if (!t || !['jpg','png','webp','pdf'].includes(t.ext)) {
        return next(new AppError('Unsupported file content', 400));
      }
    }
    ...
});
```
Serve Cloudinary PDFs with `Content-Disposition: attachment`, and never allow `image/svg+xml`.

#### SEC-10 · P1 · KYC documents (Aadhaar, PAN, bank proofs) sit unprotected on disk
**Files:** [app.js:109](apps/api/src/app.js#L109), `apps/api/uploads/kyc-documents/*.jpg`

`app.use('/uploads', express.static(...))` is registered **unconditionally**, not only in dev. Six KYC images are committed-adjacent in the working tree. Any URL under `/uploads/kyc-documents/<uuid>.jpg` is world-readable with no auth. UUIDs are unguessable, so this is not a mass breach, but a single leaked URL (email forward, browser history, referrer, support ticket) exposes a person's Aadhaar/PAN. Under the **DPDP Act 2023** that is a reportable personal-data breach.

**Fix.** Never serve KYC from a public path. Route it through an authorising controller and short-lived signed Cloudinary URLs:

```js
router.get('/kyc-doc/:userId/:docId', authenticate, authorize(['admin']), async (req, res) => {
  const doc = /* look up */;
  const signed = cloudinary.utils.private_download_url(doc.publicId, 'jpg', { expires_at: Math.floor(Date.now()/1000) + 120 });
  res.redirect(signed);
});
```
And gate the static mount: `if (!isProd()) app.use('/uploads', express.static(...))`.

#### SEC-11 · P1 · Vendors self-publish and self-feature with zero moderation
**File:** [vendors.js:324-361](apps/api/src/routes/vendors.js#L324-L361)

`VENDOR_PRODUCT_FIELDS` includes `'published'` and `'featured'`. A vendor can therefore publish a listing straight to the storefront **and mark it `featured: true`**, which is the field the homepage/`?featured=true` rail keys off. Any vendor can promote themselves into your merchandising slots. There is no listing-quality gate, no counterfeit check, no restricted-goods screening (relevant: this catalogue includes machinery and power tools).

**Fix.** Remove both fields from the vendor allowlist, add a `moderationStatus: 'draft'|'in_review'|'approved'|'rejected'` field, and only surface `published && moderationStatus === 'approved'` in the catalog. `featured` becomes admin-only or a paid, invoiced ad placement.

#### SEC-12 · P1 · Two competing self-service role-escalation endpoints, one destructive
**Files:** [users.js:47-58](apps/api/src/routes/users.js#L47-L58), [vendors.js:29-70](apps/api/src/routes/vendors.js#L29-L70)

`POST /users/become-vendor` does `{ role: 'vendor', vendorProfile: { businessName, gstin, approved: false } }` — a **whole-object replacement** that wipes existing KYC status, bank details, commission rate and earnings. `POST /vendors/onboard` does the same job correctly with `$set` on dotted paths. Both are reachable by any authenticated user.

`POST /users/become-affiliate` sets `role: 'affiliate'` but never generates `affiliateProfile.referralCode`, leaving a broken affiliate with no link to share.

**Fix.** Delete `/users/become-vendor` and `/users/become-affiliate`; keep `/vendors/onboard` and add an equivalent `/affiliates/onboard` that generates a unique referral code. Never replace `vendorProfile` wholesale.

#### PAY-02 · P0 · No CGST/SGST/IGST split, no place of supply
> **STATUS: RESOLVED for new orders — 31 Jul 2026.** `splitGst()` in

> (the P0-03 fields). Supplier state comes from the vendor's GSTIN, or `PLATFORM_GST_STATE_CODE`
> (default `33`) for admin-owned products; place of supply comes from the delivery state via

>

> In practice this means orders from vendors with no GSTIN on file carry no split. Query them
> with `db.orders.find({ 'items.igst': { $exists: false }, createdAt: { $gt: <deploy> } })`.
>
> **GST-DEAD-01 — RESOLVED 31 Jul 2026.** `gstService.js` deleted. Proven unreferenced: zero
> imports repo-wide, no barrel file in `services/`, no computed `require()` anywhere in the API,
> no tests. All three of its functions were superseded — `getRate` by `resolveTaxRate`,

> `item.hsnCode`. Immutable: editing or deleting the product afterwards leaves the order
> unchanged. Invoice templates were not touched, so nothing renders differently yet.
**Files:** [Order.js:37](apps/api/src/models/Order.js#L37), [gstService.js](apps/api/src/services/gstService.js), [invoiceService.js](apps/api/src/services/invoiceService.js)

The order stores a single scalar `gstAmount`. `gstService.calculate()` does exist and splits `cgst = sgst = gst/2, igst = 0` **unconditionally** — and is **never called by `orderController`**. Dead code that would be wrong anyway.

Correct Indian logic: compare the **supplier's** state of registration with the **place of supply** (delivery state for goods). Same state → CGST + SGST. Different state → IGST. On a multi-vendor marketplace this must be computed **per vendor per line**, because a single order can contain items from a Tamil Nadu vendor and a Maharashtra vendor shipping to Karnataka.

**Fix.** Store the split on each order item and compute per vendor:

```js
// orderItemSchema additions
gstRate: Number, taxableValue: Number,
cgst: Number, sgst: Number, igst: Number,
hsnCode: String, placeOfSupply: String, vendorGstin: String,

// helper
function splitGst({ lineTotal, rate, supplierStateCode, placeOfSupplyCode }) {
  const taxable = lineTotal * 100 / (100 + rate);   // prices are GST-inclusive
  const tax = lineTotal - taxable;
  return supplierStateCode === placeOfSupplyCode
    ? { taxableValue: +taxable.toFixed(2), cgst: +(tax/2).toFixed(2), sgst: +(tax/2).toFixed(2), igst: 0 }
    : { taxableValue: +taxable.toFixed(2), cgst: 0, sgst: 0, igst: +tax.toFixed(2) };
}
```
Add `stateCode` to `vendorProfile` (derived from GSTIN chars 1–2) and to `shippingAddress`.

#### PAY-06 · P1 · Order creation is not transactional; partial stock decrements leak
> **STOCK HALF RESOLVED — 31 Jul 2026 (MAN-STOCK-01).** `reserveStock()` in
> `services/inventoryService.js` rolls back its own successful decrements when any line fails,
> so a 5-item order failing on item 3 no longer strands the stock taken for items 1–2.
> Verified against a real MongoDB. **Still open:** the orphaned Razorpay order (created before
> the reservation) and the lack of a true multi-document transaction.
**File:** [orderController.js:160-170](apps/api/src/controllers/orderController.js#L160-L170)

```js
const stockUpdates = await Promise.all(items.map((item) =>
  Product.findOneAndUpdate({ _id: item.product, stock: { $gte: item.quantity } }, { $inc: { stock: -item.quantity } })
));
if (stockUpdates.some((r) => r === null)) {
  await Order.findByIdAndDelete(order._id);
  throw new AppError('One or more items went out of stock...', 409, 'OUT_OF_STOCK');
}
```

Each decrement is individually atomic, but the **set** is not. A 5-item order where item 4 is out of stock leaves items 1–3 decremented and the order deleted — **permanent phantom stock loss**, silently, on every partial failure. It compounds. Also: a Razorpay order was already created and is now orphaned, and `Coupon.usedCount` may already have been incremented.

**Fix.** Use a MongoDB transaction (Atlas replica sets support them):

```js
const session = await mongoose.startSession();
try {
  await session.withTransaction(async () => {
    for (const item of items) {
      const r = await Product.updateOne(
        { _id: item.product, stock: { $gte: item.quantity } },
        { $inc: { stock: -item.quantity } }, { session }
      );
      if (r.modifiedCount !== 1) throw new AppError(`Insufficient stock for ${item.title}`, 409, 'OUT_OF_STOCK');
    }
    [order] = await Order.create([orderDoc], { session });
  });
} finally { await session.endSession(); }
// create the Razorpay order only AFTER the transaction commits
```
Move the Razorpay call after the commit so you never orphan a gateway order.

#### INV-VARPRICE-01 · P0 · Variant orders are charged the parent product's price
*Found 31 Jul 2026 during INV-VARIANT-01. **RESOLVED** 31 Jul 2026.*

> **RESOLVED.** `createOrder` now prices every line from the cart snapshot (`item.price`)
> instead of re-reading `product.price`, so what the customer sees is what they are charged.
> GST, commission, the order total, the Razorpay amount and the invoice all follow from that
> one value. Historical orders are untouched.
>
> **This was broader than variants.** The same line also meant a catalogue price edit made

> Verified against a real MongoDB: a Rs.4,000 variant was billed at Rs.2,500 (undercharge),

#### COMM-PAYOUT-EARN-01 · P1 · Vendor lifetime earnings were counted twice
*Found 31 Jul 2026 during COMM-APPROVE-01. **RESOLVED** 31 Jul 2026.*

`vendorProfile.totalEarnings` had four writers. `applyEarnings` credits it on delivery and
reverses it on cancellation — an *earned* ledger. But
[admin/payouts.js:85](apps/api/src/routes/admin/payouts.js#L85) and
[:123](apps/api/src/routes/admin/payouts.js#L123) **also** incremented it when an admin recorded
a payout, so the same money was accrued a second time. A single ₹900 sale reported ₹1,800 in
lifetime earnings — reproduced against a live database.

The intent was already documented elsewhere in the codebase:
[admin/commissions.js:212](apps/api/src/routes/admin/commissions.js) carries the comment
*"do NOT increment totalEarnings here — applyEarnings already did it on delivery"*. The payout
routes simply did not follow it. `payoutService.initiatePayout` (the RazorpayX path) never
incremented either, so the two payout mechanisms also disagreed with each other.

**Fix.** Removed both increments. Delivery is now the single writer. Payout moves a commission
`approved → paid`, which is what the *derived* balances (`availableBalance`, settlement totals)
already track — none of them read `totalEarnings`. Payout amounts, commission calculations and
settlement figures are unchanged.

**Historical data is overstated and was deliberately left alone.**
`node apps/api/src/scripts/auditVendorEarnings.js` reports each vendor's stored figure against
the order ledger and prints the correction command; it writes nothing.

**Side effect:** `/admin/payouts/process` no longer reads the client-supplied `amount` at all,
which incidentally closes COMM-PAYOUT-AMT-01 for that route.

#### COMM-APPROVE-01 · P1 · Commission approval had no state machine
*Found 31 Jul 2026 during COMM-CANCEL-01. **RESOLVED** 31 Jul 2026.*

Four of the six status writers were guarded by putting the source status in the update filter.
Two were not, and both were reachable from the admin UI:

- `PATCH /admin/commissions/:id/approve` was a bare `findByIdAndUpdate` — it could flip a
  **cancelled** row back to `approved`, or a **paid** row back to `approved` so it could be paid
  a second time.
- `PATCH /admin/commissions/:id/paid` was likewise unfiltered — a **pending** row could be marked
  paid without ever being approved, and a **cancelled** row could be paid outright.

Two more were check-then-write with a real gap: `autoReleaseTransfers` and the batch payout each
selected ids by status and then wrote without re-asserting it, so a void landing in between was
silently reverted. And **no approval path anywhere checked the linked order** — `bulk-approve`
would happily approve pending rows left on orders cancelled before commission voiding existed.

**Fix.** `COMMISSION_TRANSITIONS` in `commissionService` states the machine explicitly
(`pending → approved → paid`, either non-terminal state → `cancelled`, both terminals closed).
`transitionCommission()` performs the move atomically with the legal source states in the filter,
refuses anything else with the state it actually found, and blocks approval when the order is
cancelled or returned. All four admin endpoints route through it; the two check-then-write sites
now re-assert status in their filters. Payout logic is unchanged. Verified against a real
MongoDB across 41 cases including every illegal transition and a concurrent approval race.

#### COMM-CANCEL-01 · P1 · Cancelled orders left payable commission rows
*Found 31 Jul 2026 during COMM-MAN-01. **RESOLVED** 31 Jul 2026.*

Commission rows are created at **payment**, approved by `autoReleaseTransfers` seven days after
**delivery**, and paid by `payoutService`, which checks only `status === 'approved'`. Every
marketplace cancellation path called `applyEarnings` — reversing `vendorProfile.totalEarnings`
— but **none of them touched the ledger**, so:

- an order cancelled before delivery left `pending` rows that an admin could still approve from
  the Commissions screen ([admin/commissions.js:165](apps/api/src/routes/admin/commissions.js#L165)
  filters on status only, never on the order's state);
- an order **returned or cancelled after delivery** left rows already `approved`, directly
  payable by `payoutService` with no further human step.

`orderController.cancelOrder` was worse still — it never called `applyEarnings` at all.

**Fix.** `voidCommissionsForOrder()` in `commissionService` voids `pending` and `approved` rows
and never `paid` ones, called from inside `applyEarnings`. Because all twelve reversal call
sites already route through that helper, no path can forget it. `cancelOrder` now calls it too.
Idempotent — the status filter matches nothing on a second run. Verified against a real MongoDB.

**Deliberately not covered:** recovering money already paid out. That is a manual finance
action, not something an order status change should attempt.

#### PERF-01 · P0 · Render **free** tier behind a 15-second client timeout
**Files:** [render.yaml:7](render.yaml#L7) (`plan: free`), [api.js:10](apps/web/src/utils/api.js#L10) (`timeout: 15000`)

```js
// AuthInit — don't wake the API for anonymous visitors
if (!document.cookie.includes('hasSession=1')) { dispatch(clearUser()); return; }
```

#### PERF-03 · P1 · No image optimisation anywhere
Every `<img>` in the codebase renders the raw Cloudinary URL. No `f_auto`, no `q_auto`, no `w_`/`dpr_` transformations, no `srcset`/`sizes`, no `width`/`height` attributes, no AVIF/WebP negotiation. A vendor uploading a 4 MB 4000×3000 JPEG serves that exact file into a 64×64 thumbnail.

`loading="lazy"` appears on only a handful of images (category tiles in `Home.jsx`); the product gallery, thumbnails, cart, checkout summary and search suggestions all load eagerly.

Missing `width`/`height` is also the main CLS source.

**Fix.** One helper, used everywhere:

```js
// utils/format.js
export function cdnImage(url, { w = 600, q = 'auto' } = {}) {
  if (!url?.includes('/upload/')) return normalizeImageUrl(url);
  return url.replace('/upload/', `/upload/f_auto,q_${q},w_${w},c_limit,dpr_auto/`);
}

  return widths.map(w => `${cdnImage(url, { w })} ${w}w`).join(', ');
}
```


#### PERF-04 · P1 · Product search is a regex collection scan

#### PERF-05 · P1 · Unbounded pagination and unbounded aggregation in memory
- [catalogController.js:63-65](apps/api/src/controllers/catalogController.js#L63-L65): `limit` is `parseInt(req.query.limit)` with **no cap**. `GET /api/catalog/products?limit=1000000` returns your entire catalogue in one response. Trivial DoS and a competitor's free data-scrape. (The vendor routes correctly use `Math.min(..., 100)` — the public one does not.)
- [vendors.js:139, 228, 455](apps/api/src/routes/vendors.js#L139): `Order.find({ 'items.vendorId': vendorId })` with **no limit**, then `.forEach` in JavaScript. A vendor with 50,000 orders OOMs the process on a dashboard load.
- [catalogController.js:103-106](apps/api/src/controllers/catalogController.js#L103-L106): two `Product.distinct()` calls over the whole collection on every `/catalog/categories` request (cached, but the cache is per-process in-memory).
- [catalog.js:17](apps/api/src/routes/catalog.js#L17): `/catalog/brands` runs `distinct` uncached on every call.

**Fix.** Cap `limit` at 100. Replace the vendor loops with `$aggregate`:

```js
const [agg] = await Order.aggregate([
  { $match: { 'items.vendorId': vendorId, createdAt: { $gte: startDate } } },
  { $unwind: '$items' },
  { $match: { 'items.vendorId': vendorId } },
  { $group: { _id: null,
      sales:    { $sum: { $multiply: ['$items.price', '$items.quantity'] } },
      earnings: { $sum: '$items.vendorEarning' } } },

```
Cache `/catalog/brands` and `/catalog/categories` for 1 hour; invalidate on product/category writes.

#### PERF-06 · P2 · Misc
- The in-memory cache `Map` ([cache.js:3](apps/api/src/utils/cache.js#L3)) has **no size cap** and is keyed on `req.originalUrl` — an attacker varying query strings grows it without bound until the process dies. Add an LRU cap (e.g. `lru-cache`, max 5000).

Self-host Inter as a `woff2` subset instead; you eliminate two DNS lookups and two TLS handshakes.
- Only `compression()` (gzip) on the API. Vercel handles brotli for static assets, so this is OK, but the API JSON responses are gzip-only.
- No service worker, no offline shell, no PWA manifest.
- `<div id="initial-loader">` with `position:fixed;inset:0` is removed 200 ms after `main.jsx` executes — but React's first paint happens after the lazy route chunk loads, so there is a visible white gap between loader removal and content.

#### BE-01 · P1 · No health check, no graceful shutdown, no crash handlers
**File:** [server.js](apps/api/src/server.js)

19 lines. There is no `GET /health` — a request to it falls through to `app.all('*')` and returns a 404, so any platform health probe marks the service unhealthy. No `SIGTERM` handler, so Render kills the process mid-request during deploys, dropping in-flight orders. const server = app.listen(PORT, ...);

```js
  console.log(`${sig} received, draining…`);
  server.close(async () => { await mongoose.connection.close(); process.exit(0); });
  setTimeout(() => process.exit(1), 15000).unref();
}
['SIGTERM','SIGINT'].forEach(s => process.on(s, () => shutdown(s)));
process.on('unhandledRejection', (r) => { console.error('UNHANDLED REJECTION', r); });
process.on('uncaughtException', (e) => { console.error('UNCAUGHT', e); shutdown('uncaughtException'); });
```

#### BE-02 · P1 · Background jobs run in-process with `setInterval` and no locking
**File:** [scheduler.js](apps/api/src/jobs/scheduler.js)

Eight jobs on `setInterval`, in the web process. Three problems:
1. **The moment you run 2 instances, every job runs twice** — duplicate abandoned-cart emails, duplicate review requests, and `autoReleaseTransfers` / `payoutService` double-crediting vendor earnings. That last one is a money bug waiting for your first horizontal scale.
2. On Render free the instance sleeps; jobs simply don't run.
3. Jobs compete with request handling for the same event loop. `reconcilePayments` iterating orders will add latency to checkout.

**Fix.** Short term, add a Redis lock:
```js
async function withLock(name, ttlMs, fn) {
  const redis = getRedis(); if (!redis) return fn();
  const ok = await redis.set(`lock:${name}`, process.pid, 'PX', ttlMs, 'NX');
  if (!ok) return;
  try { await fn(); } finally { await redis.del(`lock:${name}`); }
}
```
Medium term, move to BullMQ with a separate worker process (`startCommand: node apps/api/src/worker.js`) and Render Cron Jobs for the scheduled triggers.

#### BE-03 · P1 · No request validation layer

```js
router.post('/', authenticate, validate(z.object({
  body: z.object({ productId: z.string().regex(/^[a-f\d]{24}$/i), rating: z.number().int().min(1).max(5),
                   title: z.string().max(120).optional(), body: z.string().max(2000).optional() })
```

#### BE-04 · P1 · Vendor product price inflates compounding on every edit
**File:** [vendors.js:334-340, 367](apps/api/src/routes/vendors.js#L334-L340)

```js
function normalizePriceToInclusive(data) {
  if (!data.taxIncluded && data.taxRate > 0 && data.price > 0) {
    data.price = parseFloat((data.price * (1 + data.taxRate / 100)).toFixed(2));
    ...
  }
  data.taxIncluded = true;
}
router.put('/products/:id', ..., normalizePriceToInclusive(allowed), ...);
```

On `PUT`, `allowed` contains only the fields the client sent. If a vendor edits a product and the form posts `{ price: 118, taxRate: 18 }` **without** `taxIncluded`, the guard `!data.taxIncluded` is true and the price becomes **139.24**. Edit again → 164.30. Every save inflates the price by the tax rate, permanently.

The frontend may currently always send `taxIncluded`, which would mask this — but the API is public and the invariant is not enforced.

**Fix.** Only normalise when the request explicitly declares the price is exclusive:
```js
function normalizePriceToInclusive(data) {
  if (data.taxIncluded === false && data.taxRate > 0 && data.price > 0) {
    data.price = +(data.price * (1 + data.taxRate / 100)).toFixed(2);
    if (data.compareAt > 0) data.compareAt = +(data.compareAt * (1 + data.taxRate / 100)).toFixed(2);
    data.taxIncluded = true;
  }
}
```
Better: store `priceExclusive` and `taxRate` as the source of truth and derive the inclusive price for display. Never mutate a stored price in place.

#### DB-01 · P1 · `User` is a god object
[User.js](apps/api/src/models/User.js) is 175 lines holding: auth, addresses, wishlist, a 40-field `vendorProfile` (including bank account, IFSC, PAN, GSTIN, KYC docs, commission rules, earnings) and a 45-field `affiliateProfile` (including a *second* set of bank details in both `kycData` and `bankDetails` — duplicated, unreconciled).

```js
userSchema.index({ email: 1 }, { unique: true });   // ensure it exists
```

#### DB-02 · P1 · No TTL indexes, unbounded growth collections
No `expireAfterSeconds` anywhere. Collections that grow forever with no retention policy:

```js
notificationSchema.index({ createdAt: 1 }, { expireAfterSeconds: 60*60*24*180 });
```

#### DB-03 · P1 · The category model is doubled and inconsistent
`Product` carries **both** `category: String` (comment: *"legacy slug"*) and `categoryIds: [ObjectId]`. Every read path has to handle both:
```js
filter.$or = [{ categoryIds: catDoc._id }, { category: category.toLowerCase() }];
```
This appears in `catalogController`, the vendor CSV export, `recommendations`, and the admin filters. Every query on category is an `$or` across two differently-typed fields, which fragments index usage. The `{ categoryIds: 1, published: 1, price: 1 }` compound index cannot serve the `$or` branch that filters on `category`.

**Fix.** Write a migration: for every product, resolve `category` → `Category._id`, push into `categoryIds`, then `$unset` the string field. Drop it from the schema and delete every `$or` branch. Do this before the catalogue grows.

#### DB-04 · P2 · Missing data model for B2B essentials
No schema exists for, and therefore no feature can exist for:
- **Product downloads** — manuals, datasheets, CAD/STEP files, installation guides, CE/ISI certificates. There is `videoUrl` (never rendered) and nothing else.
- **Compatibility / fitment** — which machines a spare part fits. This is *the* defining feature of a spare-parts marketplace.
- **OEM / cross-reference part numbers** — buyers search by the OEM number, not your SKU.
- **Tiered / slab pricing** — `price` is a single scalar. No `priceBreaks: [{ minQty, price }]`.
- **MOQ** — no minimum order quantity.
- **RFQ / quotations** — no `Quote` model, no negotiation thread.
- **Units of measure** — no `unit` field (piece / metre / kg / box of 100). Industrial catalogues are unusable without it.
- **Buyer organisations** — no `Organization` model, so no multi-user company accounts, no approval workflows, no spend limits. Amazon Business's core B2B feature.

**Fix.** These are additive schema changes; design them together rather than one at a time (see §10).

#### DB-05 · P2 · Misc
- `Order.status` has **13** enum values including both `pending`/`pending_payment` and `placed`/`paid`/`confirmed`. Nobody can tell you the difference between `placed` and `confirmed`. `getOrders` has to hand-map groups. Reduce to 7: `created → paid → processing → shipped → delivered`, plus `cancelled`, `returned`.
- `Order.shippingAddress` is embedded (correct — it must be a snapshot) but `items[].price` is also snapshotted while `createOrder` reads the **live** `product.price` to compute the total, so a cart shown at ₹5,000 can be charged at ₹5,500 with no warning. Snapshot the price at add-to-cart, then re-validate and *tell the user* if it changed.
- No `Order` index on `orderId` beyond the implicit unique — fine — but no index on `{ 'items.vendorId': 1, status: 1 }`, which is the vendor order-counts query ([vendors.js:558-566](apps/api/src/routes/vendors.js#L558-L566), 7 parallel `countDocuments`).
- `Product.slug` is `unique: true, sparse: true` but `slugify(title)` is used without a collision suffix ([vendors.js:347](apps/api/src/routes/vendors.js#L347)) — two vendors listing "Angle Grinder 4 Inch" produce a duplicate-key error the vendor sees as an opaque 409.
- No soft deletes anywhere. `DELETE /vendors/products/:id` hard-deletes a product that may be referenced by historical orders and warranties, breaking the order history display.

- No `/health` endpoint for a probe to hit (BE-01).
- No documented backup or restore procedure. MongoDB Atlas free/shared tiers have limited backup; nobody has tested a restore.
- No staging environment. `render.yaml` defines exactly one service.
- No Dockerfile → the build is not reproducible; `buildCommand` is a shell one-liner chaining `cd` and `npm install`.
- No `engines` field in either `package.json` → Render picks whatever Node it defaults to, which can change under you.

**Fix, in priority order:**
1. Render Starter plan + a staging service (~$14/mo total). This removes cold starts and gives you a place to test.
2. Sentry on both API and web (free tier is sufficient) — 30 minutes of work, immediately reveals errors you currently cannot see.
3. UptimeRobot on `/health`, 1-minute interval, alerting to WhatsApp.
4. Atlas M10 with continuous backups, and **actually perform a test restore** and document it.
5. `"engines": { "node": ">=20 <21" }` in both packages.
6. Dockerfile + `docker-compose.yml` for reproducible local and CI builds.

#### UX-03 · P1 · Accessibility is near-zero
Across ~110 components there are **63 total occurrences** of `aria-label`, `loading=`, `width=` and `srcSet` *combined*. Specific failures:

- **Gallery arrows** ([Product.jsx:272-283](apps/web/src/assets/pages/Product.jsx#L272-L283)) — `<button>` with only an icon, no `aria-label`. A screen reader announces "button".
- **Dot indicators** ([Product.jsx:286-290](apps/web/src/assets/pages/Product.jsx#L286-L290)) — same, plus no `aria-current`.
- **Accordion** ([Product.jsx:20](apps/web/src/assets/pages/Product.jsx#L20)) — no `aria-expanded`, no `aria-controls`.
- **Search autocomplete** ([Header.jsx:114-149](apps/web/src/assets/components/layout/Header.jsx#L114-L149)) — no `role="combobox"`, no `aria-autocomplete`, no `aria-activedescendant`, **no arrow-key navigation**. Keyboard users cannot select a suggestion.
- **Radio groups** in Checkout use `className="sr-only"` on the input inside a `<label>` — technically focusable, but there is **no visible focus ring**, so a keyboard user cannot see where they are.
- **Star ratings** are rendered as five `<Star>` SVGs with no `role="img"` and no text alternative.
- **Quantity ± buttons** use the characters `−` and `+` with no labels.
- **No skip-to-content link.**
- **No focus trap** in the mobile menu or the cart drawer; focus is not returned on close.
- **Colour contrast:** `#8898b3` on the dark hero (`#162035`) ≈ 4.3:1 — fails WCAG AA for the 14 px body text it is applied to. `#64748b` on `#130d05` in the CTA block ≈ 3.9:1 — fails. `text-secondary-400` on white is used for metadata throughout and is likely below 4.5:1.
- **Touch targets:** the thumbnail buttons are 64×64 (fine), but the dot indicators are **6×6 px** — far below the 44×44 minimum in WCAG 2.5.8.

This is not only an ethics/compliance issue — India's **RPwD Act 2016** requires accessible digital services from entities providing goods to the public, and large enterprise buyers increasingly require a VPAT before onboarding a supplier.

**Fix.** Run `axe-core` in CI (`@axe-core/playwright`), fix every serious/critical violation, and adopt Radix UI or Headless UI for the accordion, dialog, combobox and radio-group primitives rather than hand-rolling them.

#### UX-05 · P1 · Category and search filters are unusable at scale
**File:** [Search.jsx:28-157](apps/web/src/assets/pages/Search.jsx#L28-L157)

- **Brand is a single-select `<select>`.** With 200 brands this is a scroll-hell dropdown; with 2 brands it is fine. You cannot select "Bosch OR Makita". Every competitor uses multi-select checkboxes with counts and a search-within-filters box.
- **Category is also single-select**, and only top-level (`filter(c => !c.parentId)`) — subcategories are unreachable from the filter panel.
- **No "In Stock only" filter.** Out-of-stock items pollute every result page.
- **No facet counts** — the user cannot see "Bosch (43)" before clicking.
- **No attribute facets** — voltage, power (W), chuck size, phase, material, IP rating. `Product.specifications` is a free-text `[{label, value}]` array, so faceting on it is impossible without a schema change. This is the single biggest gap versus Zoro/Grainger.
- **No active-filter chips** — the user sees a count badge but not *what* is applied.
- **No "relevance" sort** for search results (sorts are Featured/Newest/Price/Rating only).
- **No infinite scroll or "load more"** on mobile — numbered pagination only.
- **No results-per-page control.**

**Fix.** Convert `specifications` to a typed `attributes: Map<string, string|number>` with a per-category attribute schema, then build facets with a MongoDB `$facet` aggregation (or move to Atlas Search / Typesense which gives you facet counts for free). Convert brand and category to multi-select checkbox lists with counts.

#### UX-06 · P2 · Misc UI
- **`ErrorBoundary.jsx` exists and is imported nowhere.** A render error in any page white-screens the entire app. Wrap `<Suspense>` in it in `App.jsx`.
- `RequireAuth` returns `null` while `isInitialized` is false ([App.jsx:152](apps/web/src/App.jsx#L152)) — a blank white screen, not a loader, on every protected route load.
- Loading states are inconsistent: `Home` uses skeletons, `Product` uses a centred spinner, `Search` passes `loading` to `ProductGrid`, `Checkout` uses a full-page spinner. Pick one system.
- Empty states: `Search` renders `ProductGrid` with no products and no "no results" messaging or recovery suggestions ("did you mean…", "browse this category instead").
- Error states: almost everything is a `react-hot-toast` error. A toast disappears in 4 seconds; a failed checkout needs an inline, persistent, actionable error.
- `onError={(e) => e.currentTarget.remove()}` ([Product.jsx:267](apps/web/src/assets/pages/Product.jsx#L267)) removes the image node on load failure, collapsing the layout. Use a placeholder.
- **No dark mode.** No CSS custom properties for colour; every value is a Tailwind class or an inline hex. Retrofitting will be expensive — introduce semantic CSS variables now (`--color-surface`, `--color-text`) even if you only ship light mode.
- Inline `style={{...}}` objects are used heavily in `Home.jsx` and `Header.jsx` alongside Tailwind classes. Two styling systems in one file.
- The logo SVG uses `<text fontFamily="Arial Black">`, which renders differently on Windows, macOS, Android and Linux. Convert to a path.

## 7. Revenue Optimisation

1. **Homepage product rails** (UX-01) — a homepage with zero products has a near-zero add-to-cart rate from organic landings. This is the highest-value single change available.
2. **Fix the coupon input** (PAY-05) — you have a complete promotions engine that no customer can use. Every discount campaign you have ever planned was silently a no-op.
3. **Guest checkout** (PAY-09) — Baymard's abandonment research consistently puts forced account creation in the top 3 causes, at ~24–26%.
4. **GSTIN capture** (PAY-04) — B2B buyers without ITC pay 18% more. You are not price-competitive to them at all today.
5. **Tiered pricing + MOQ** — the cleanest AOV lever in industrial commerce. "5+ units ₹X, 25+ units ₹Y" converts browsers into bulk buyers.
6. **Free-shipping threshold nudge** — `Setting 'shipping.free_threshold'` defaults to ₹5,000 and is **never shown to the user**. Add "Add ₹1,240 more for FREE delivery" to the cart drawer. Typically a 5–15% AOV lift.
7. **Abandoned cart recovery** — `abandonedCartService` exists and runs, but emails are dead because `RESEND_API_KEY` isn't in Render (DEV-03). Fix the env var and this feature starts working immediately.
8. **Back-in-stock alerts** — `StockAlert` model + subscribe endpoint exist. There is no job that actually *sends* the alert when stock returns. Finish it.
9. **Frequently-bought-together / accessories** — consumables (blades, bits, discs, filters) attached to machines is the classic industrial attach-rate play. 10–20% AOV.
10. **Vendor ads** — the `AdCampaign`/`AdWallet` machinery is built. Fix SEC-01 first, then actually place sponsored slots in search results. This is high-margin marketplace revenue.
11. **Reduce the "Recommended" friction in payment** — merge shipping+payment into one step. Every step in a funnel costs conversions, and step 3 currently offers exactly one option.
12. **Price-drop and quote-follow-up emails** — you have the buyer's email and their viewed products (`recently_viewed` in localStorage — move it server-side).

## 11. RC-03 — Favicon, robots.txt and per-route SEO (2026-08-05)

Scope: the reported symptom was "the favicon does not show in Google results".
The root cause was a single measurable fact, and the surrounding SEO defects that
were cheap to close at the same time were closed. Nothing else was touched.

### FAV-01 · The favicon was not square

**Root cause.** `apps/web/public/favicon.png` was **1655 × 950 px** — a rectangle —
and 895,951 bytes. Google's favicon requirements state the icon must be a square
(a multiple of 48 px is recommended). A non-square file is dropped without a
Search Console warning, which is why the icon never appeared. `index.html`
compounded it by declaring that file as `sizes="32x32"`, which was false.

Two secondary faults made the fallbacks useless as well:
- `favicon.svg` drew its "M" with `<text font-family="Arial Black">`. A rasteriser
  without that font produces a blank brown hexagon.
- `apple-touch-icon` pointed at `logo.png` — a 1024 × 1024, 928 KB *wordmark*,
  unreadable at 180 px.

**Fix.** The mark was decoded from `favicon.png`, cropped to its ink bounding box
(x 496–1145, y 72–843) with 14 % padding, and resampled with an area-average
filter into genuine squares. No image library exists in this repo and none was
added; `apps/api`-style scratch tooling did the decode/encode with node's `zlib`.

| File | Size | Bytes | Purpose |
|---|---|---|---|
| `favicon.ico` | 48², 96² | 12,273 | root-convention fallback, PNG payloads |
| `favicon.png` | 96 × 96 | 9,078 | primary — *same URL Google already crawls* |
| `favicon-192.png` | 192 × 192 | 31,934 | Android / high-DPI |
| `favicon-512.png` | 512 × 512 | 199,427 | Organization schema logo |
| `apple-touch-icon.png` | 180 × 180 | 28,087 | iOS home screen |
| `og-image.png` | 1200 × 630 | 153,390 | the social card that was being lied about |

`favicon.svg` was rewritten with the M as a `<path>` — three paths, zero fonts.

**Expect a delay.** Google re-fetches favicons on its own crawl schedule; this is
typically days to a few weeks after the homepage is re-crawled. Requesting
indexing for `https://www.macgly.com/` in Search Console is the only way to
hurry it. There is nothing further to change in the code.

### SEO-02 · Canonical and OG tags leaked between routes — **FIXED**

`setMeta` guarded the canonical write with `if (canonical)` and had no removal
path at all, so a route that passed no canonical inherited the previous route's —
or, on a cold load, the homepage's hardcoded one. `og:image` behaved the same way:
Product → `/track-order` kept the product photo.

`apps/web/src/utils/seo.js` now writes **every** tag it owns on every call:
- canonical defaults to `SITE_URL + pathname` with the query string dropped, which
  is what collapses `/products?sort=x&page=2` onto `/products`;
- `SITE_URL` is hard-coded rather than read from `window.location.origin`,
  because `render.yaml` builds the SPA and the API serves it — deriving the origin
  would make `macgly.onrender.com` declare *itself* canonical;
- a missing description/image now **removes** the stale tag instead of keeping it;
- `og:image:width/height` are emitted only for the known 1200 × 630 card, never
  for an arbitrary product photo;
- `removeJsonLd()` clears the Product schema when leaving a product page.

Ten routes that never called `setMeta` now do: `/blog/:slug`, `/track-order`,
`/warranty-check`, `/store/:id`, `/info/privacy`, `/info/terms`, `/sell`,
`/affiliate`, plus `noindex` on `/cart` and the 404 page — the SPA fallback
returns HTTP 200 for unknown URLs, so `noindex` is the only signal a crawler gets.
`/track-order` goes `noindex` the moment an order id is in the URL.

### SEO-03 · robots.txt — **FIXED** (see the correction inline above)

`apps/web/public/robots.txt` is now the single source of truth, and says so.
Changes: real parameter names (`minPrice`/`maxPrice`/`minRating`/`inStock`, not
the fictional `min`/`max`/`q`/`filter`); a `&name=` rule beside every `?name=` rule,
because `/*?page=` alone never matches `…&page=2`; `Disallow: /api/`;
`Disallow: /cart`; `Disallow: /track-order?` (that URL carries an order id **and**
a customer phone number); `Disallow: /*?ref=` and `/*&ref=` (affiliate links are
the canonical URL plus `?ref=CODE`, applied to *every* route by
[App.jsx:139](apps/web/src/App.jsx#L139) — unblocked, they duplicate the whole site
once per affiliate); and explicit `Allow:` lines for the icons, since Google will
not display a favicon it cannot fetch.

The dead `/robots.txt` rewrite was removed from `vercel.json` (Vercel serves
`public/` before rewrites, so it never fired) and the divergent hand-written
robots in [app.js](apps/api/src/app.js) was replaced by a host guard: because
`render.yaml` builds `apps/web` and the API serves `apps/web/dist`,
`macgly.onrender.com` answers with the entire storefront and was inviting Google
to index the catalogue under a second hostname. Any host that is not
`FRONTEND_URL` now gets `Disallow: /`; the canonical host falls through to the
static file.

Also: `/info/faq`, `/info/buyer-guide` and `/info/seller-guide` were missing from
the sitemap and are now listed; `<html lang>` is `en-IN`.

### Not done, deliberately

## 12. RC-SEO-04 — Final SEO production hardening (2026-08-05)

Every RC-SEO-03 finding was re-proved before anything was changed. One was wrong
and is retracted below. Three P0s and seven P1/P2 items were real and are closed.

### Retraction — "no breadcrumb UI on any route"

**This was wrong.** [Product.jsx:245](apps/web/src/assets/pages/Product.jsx#L245) and
[Category.jsx:161](apps/web/src/assets/pages/Category.jsx#L161) both render a `<nav>`
breadcrumb. My sweep detected breadcrumbs by `nav[aria-label*=breadcrumb]` or a
`.breadcrumb` class; these use neither, so the detector missed them and I reported
the absence of my selector as the absence of the feature. Only the
**BreadcrumbList structured data** was genuinely missing. Same lesson as the
INV-DL-01 retraction: a tool's view of the code is not the code.

### P0-1 · /sitemap.xml served HTML — FIXED

Reproduced before the change: `200`, `text/html`, 0 `<loc>`, byte-identical to the
SPA shell — and confirmed on live production. `app.get(path, Router)` does not
rewrite `req.url`, so the router's `router.get('/')` never matched and the SPA
catch-all answered. One word: `app.get` → `app.use`. Now `200`,
`application/xml`, 20 URLs.

### P0-2 · Homepage metadata in every server response — FIXED for dynamic routes

Reproduced on 6/6 route types. Cause is SPA rendering, not server routing: one
static `index.html` answers every URL and `setMeta` runs in a `useEffect`.

**The hosting check changed the fix.** `curl -I https://www.macgly.com/` returns
`Server: Vercel` — the document is served statically from `dist/`, so Express
never sees it and middleware-based injection would have fixed nothing on the
public domain. The smallest solution compatible with React + Vite + Express, with
no framework migration, is **build-time metadata prerendering**:
[apps/web/scripts/prerender.mjs](apps/web/scripts/prerender.mjs) writes
`dist/<route>/index.html` per product, category, blog post and vendor store.
Vercel serves static files before applying rewrites — the same precedence that
already makes `public/robots.txt` beat the `vercel.json` rewrite — so those files
win over the SPA fallback. Chained into `npm run build`; if the API is
unreachable it logs, exits 0, and routes fall back to today's behaviour.

Two follow-on defects surfaced during validation and are fixed:
`express.static` was 301-ing `/product/x` → `/product/x/` once directories
existed (two URLs per page, neither matching the sitemap) — fixed with
`redirect: false`; and the Express catch-all now prefers a prerendered shell so
the Render origin serves the same bytes as Vercel instead of different metadata.

Static routes (`/products`, `/info/*`) are **not** prerendered: their copy lives
in JSX and duplicating it here would drift. They already resolve correctly for
Googlebot, which renders JavaScript.

### P0-3 · Vendor store unreachable — FIXED

Three distinct faults, all reproduced:
1. `GET /api/vendors/:id/public` returned **401**. The handler commented *"Public
   vendor store info"* sat 1,576 lines below `router.use(authenticate)`. Moved above it.
2. [VendorStore.jsx](apps/web/src/assets/pages/VendorStore.jsx) called `/products` → **404**;
   the catalogue is at `/api/catalog/products`.
3. `?vendor=` was not a supported filter, so once (2) was fixed the store would
   have listed **every product on the site**. Added to `getProducts`.

Also: the handler counted `{ status: 'approved' }`, but `Product` has no `status`
field — it uses `published`. Every store read "0 products". And the page's
metadata read `vendorProfile.description` while the API returns `storeDescription`
at the top level, which the rest of the component already used correctly.

### P1 / P2 closed

- **BreadcrumbList** on product and category pages, mirroring the existing `<nav>`.
- **BlogPosting** on posts, **FAQPage** on `/info/faq` (all 20+ Q&As, verified visible on the page).
- **Product offers** gained `url`, `itemCondition`, `seller` (the listing vendor), and a top-level `url`.
- **Soft 404s** — unknown product slug and unknown vendor id now emit `noindex` instead of the homepage canonical.
- **/login and /register** were the other two members of the four-route duplicate-title cluster; both now self-canonical and `noindex`.
- **Vendor stores in the sitemap**, restricted to vendors with at least one published listing.
- **Blog publish-field mismatch** — the sitemap now matches `status: 'published'` **or** the legacy `isPublished`, so it can no longer advertise a URL the public API would 404.
- `injectJsonLd` accepts several schemas and emits one `@graph`, so a single `#json-ld` element is still cleared on navigation.

### Deliberately NOT emitted

`offers.shippingDetails` and `offers.hasMerchantReturnPolicy` are omitted, and
that is a decision rather than an oversight. Shipping is a live per-pincode
Delhivery rate with per-product overrides — no flat figure would be true. And the
published return window (**7 days**, [Faq.jsx](apps/web/src/assets/pages/info/Faq.jsx))
contradicts the one the API enforces (**30 days**,
[returns.js:23](apps/api/src/routes/returns.js#L23)). Google will warn about the
omission; that is the correct trade against publishing a claim the business does
not honour. **Reconcile the two policies and this becomes a two-line change.**
